### MySQL 은? 
MySQL 서버는 크게 **MySQL 엔진**과 **스토리지 엔진**으로 구분됨. 

**MySQL 엔진**은 커넥션 핸들러와 SQL 파서 및 전처리기, 옵티마이저가 중심을 이룸. 요청된 SQL 문장을 분석하거나, 최적화하는 처리들을 담당해서 수행한다. 

**스토리지 엔진**은 실제 데이터를 디스크로부터 읽어오거나 저장하는 역할을 전담함. MySQL 엔진이 두뇌에 해당한다면 스토리지 엔진은 손과 발에 해당한다. MySQL 서버에서 스토리지 엔진은 여러 엔진을 동시에 사용이 가능하다. 

>MySQL 서버가 스토리지 엔진에 쿼리 요청을 전달할 때 사용하는 인터페이스를 핸들러 API라고 한다. MySQL 엔진은 스토리지 엔진과 이 핸들러 API를 통해 데이터를 주고 받는다.


## 쿼리 평가 엔진. 

SQL 구문을 분석하고 어떤 순서로 기억장치의 데이터에 접근할지를 결정함. 
이때 결정되는 계획을 '실행계획'이라고 함. 이런 실행 게획에 기반을 둬서 데이터를 접근하는 방법을 접근 메서드라 부름. 


### MySQL은 ?

MySQL의 전체적인 쿼리 실행 구조는 다음과 같음. 

쿼리파서 -> 전처리기 -> 옵티마이저 -> 쿼리 실행 엔진 -> (스토리지 엔진)

**쿼리파서**는 사용자 요청으로 들어온 SQL 쿼리를 토큰으로 파싱해서 트리 형태의 구조로 만들어낸다. 이를 구문 트리(AST, Abstract Syntax Tree) 생성이라고 한다. 이 과정에서 SQL 구문의 기본적인 문법 오류(Systax)는 이 과정에서 걸러지게 된다. 
```sql
-- 올바른 문법
SELECT id, title FROM post;

-- 잘못된 문법 (파서에서 에러 발생)
SELECT FROM post;
-- → Syntax error: SELECT 구문에 컬럼명이 누락됨
```

**전처리기**는 앞서서 파싱된 트리를 기반으로 메타데이터(테이블, 컬럼, 함수 존재 여부 등) 확인한다. 각 토큰이 의미하는 테이블 이름, 컬럼 이름, 내장 함수들이 실제로 존재하는지, 접근 권한이 있는지 등을 확인하는 과정들이 수행된다. 즉, 실제로 사용 가능한지, 구조적으로 유효한지 검증한다. 이때 실제로 존재하지 않거나, 사용할 수 없는 경우 걸러지게된다. 

```sql
SELECT * FROM post; 
```
- 예시, 문법 구조는 맞으나 post 테이블이 실제로 존재하지 않는 경우.

**옵티마이저** 
옵티마이저는 SQL 쿼리문장을 가장 저렴한 비용으로 빠르게 처리하는 방법을 결정하는 역할을 한다.쿼리 성능을 좌우하는 중요한 파트라고 볼 수 있다. 옵티마이저가 결정하는 실행 계획에 따라 전체적인 쿼리 성능이 결정된다. 

**쿼리 실행 엔진**
쿼리 실행 엔진은 옵티마이저로부터 넘겨받은 실행 계획을 핸들러(스토리지 엔진)와 상호작용하면서 명령을 내리고, 결과를 받고 취합하면서 쿼리를 수행하는 역할을 한다. 옵티마이저가 짠 계획대로 쿼리를 (스토리지 엔진과 함께) 수행해서 결과를 만들어내는 주체라고 할 수 있다.


## 버퍼 매니저. 

DBMS는 버퍼라는 메모리 영역을 적극적으로 활용함. 이 메모리 영역에 디스크에 있는 데이터를 페이지 단위로 올려서 읽기/쓰기 성능을 향상시키는 메모리 캐시 역할을 수행함. 

버퍼 풀은 대략 다음과 같은 방식으로 동작함. 

1. 쿼리를 요청 받으면 해당 페이지가 버퍼 풀에 존재하는지 확인함. 있다면 사용. (캐시 힛)
2. 만약 존재하지 않는다면 디스크에서 읽어와 버퍼에 적재 후 사용 (캐시 미스)
3. 변경된 페이지는 `dirty page`로 표시되고
4. 일정 시간(조건)이 지난 후 디스크에 일괄 flush 된다.

### MySQL은? : InnoDB 버퍼 풀
MySQL에는 InnoDB 스토리지 엔진에 Buffer Pool 메모리 관리자가 존재함. 
이 역시 MySQL 성능의 핵심 구성 요소 중 하나이다. 

디스크의 데이터 파일이나, 인덱스 정보를 메모리에 캐시해두는 공간. 쓰기 작업을 지연해서 일괄적으로 처리할 수 있도록 버퍼 역할도 해준다. 



## 디스크 용량 매니저

DBMS는 데이터를 영구적으로 저장할지를 관리함. 데이터의 읽고 쓰기를 제어한다. 



## 트랜잭션 매니저, 락 매니저 

DBMS에서는 여러 사람들이 동시에 데이터베이스에 접근해서 사용하게됨. 이때 각각의 처리는 DBMS 내부에서 트랜잭션이라는 단위로 관리가 된다. 

트랜잭션은 닥업의 완전성을 보장하기 위한 기능으로 일련의 작업들이 모두 처리되거나 실패하도록 하여서 작업의 일부만 반영되고 일부는 반영되지 않는 반쪽짜리 작업을 만들기 않게 하기 위한 기능이다. 즉, 데이터의 정합성을 보장하기 위한 기능이다. 이러한 기능을 지원하도록 돕는 것이 트랜잭션 매니저의 역할이다. 

락은 동시성을 제어하기 위한 기능이다. 만일 동일한 레코드에 여러 커넥션이 달라붙어 동시에 데이터를 변경해버리면, 데이터의 신뢰성을 잃어버릴 수 있다. 때문에, 동시에 레코드에 접근했더라도 하나의 요청만 데이터에 접근할 수 있도록 하는 기능이 잠금이고, 이를 락 매니저가 관리한다.

### MySQL은?

MySQL은 스토리지 엔진들에 따라서 트랜잭션 지원 여부가 다른다. 대표적으로 InnoDB는 트랜잭션을 지원하지만, MyISAM이나 MEMORY 스토리지 엔진은 트랜잭션을 지원하지 않는다.


#### MVCC?
레코드 레벨의 트랜잭션을 지원하는 DBMS에서 제공하는 기능이다. 이 기능은 하나의 레코드에 여러개의 버전이 유지되는 기능이다. 잠금을 사용하지 않으면서 일관된 읽기를 제공하기 위해서 고안되었다. InnoDB에서는 이 기능을 Undo Log를 통해서 구현한다.
