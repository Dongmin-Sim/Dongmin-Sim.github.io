### 문제발생. 현상파악.

Phase-2의 **피크 테스트**에서 목표했던 TPS와 응답시간을 충족하지 못했습니다.
피크 테스트의 목표 했던 TPS는 오차 포함 `31 TPS` 이상이 나오길 기대했지만, 결과는 그에 좀 못미치는 `28.5 TPS`를 보였습니다. 전체 응답중 상위 95%의 응답시간을 나타내는 `P95` 지표도 581ms로 목표했던 300ms를 훌쩍 뛰어넘는 결과가 나왔습니다.


왜 이런 테스트 결과가 나왔는지 테스트 중 기록된 모니터링 내용을 보면서 원인을 파악해보겠습니다.
첫번째로 할 수 있는 것은 **현재 시스템의 병목지점**을 찾는 것. 

![Desktop View](/assets/images/performance-test-2/phase-2-cpu-usage.png){: width="1072" height="589" }_CPU 사용률_

먼저 서버의 상태정보부터 확인해봅니다. 좌측은 애플리케이션 서버의 `CPU 사용률`을 나타낸 그래프이고, 우측은 DB 서버의 `CPU 사용률`을 나타낸 그래프입니다. 제일 먼저 눈에 띄는 점은 Application 서버와 DB서버의 `CPU 사용률`에서 큰 차이가 발생했다는 점이었습니다. 애플리케이션 서버의 `CPU 사용률`은 꾸준하게 20% 아래를 유지하고 있지만, DB 서버의 경우 꽤 높은 `CPU 사용률`을 보이고 있습니다.

꾸준하게 60%의 사용률을 보이다 어느 시점을 기준으로 결국 CPU 사용률이 80% 초과해 100%에 달성한 것을 확인할 수 있었습니다. 

CPU 사용률이 100%라는 것은 CPU가 쉴새없이 일을 처리하고 있는 상태입니다. 이 상태에서는 추가적인 요청이 들어오더라도 추가 작업을 처리할 수 없는 상태가 됩니다. 이는 DB 서버에서 시스템 자원을 모두 사용할 정도로 바쁘게 작업이 이루어지고 있음을 뜻합니다. 즉, **DB 서버에서 병목이 발생**했음을 확인할 수 있었습니다.

만일 DB 서버에서 병목이 발생했다면, 사용 가능한 DB 커넥션풀도 모두 고갈되었을 확률이 높습니다. 

![Desktop View](/assets/images/performance-test-2/phase-2-connection-pool.png){: width="1072" height="589" }_DB 커넥션 풀_

예상했던 대로 이전에도 간간히 MAX 커넥션 사용률을 보이다, 특정 시점에 DB 커넥션풀을 모두 소진하고, Pending 요청수도 계속 증가하면서 지속되는 것을 확인할 수 있었습니다. `Pending`은 커넥션 풀에서 DB 커넥션을 획득하려고 대기 중인 요청의 수를 나타냅니다. 

그와 비슷한 시기에, 존재하던 톰캣 스레드도 모두 busy 상태로 block이 되면서 Application 서버에서도 더 이상의 추가적인 요청 처리가 어려운 상태로 대기 중이었을 가능성이 높습니다. 
![Desktop View](/assets/images/performance-test-2/phase-2-tomcat-threads.png){: width="1072" height="589" }_DB 커넥션 풀_


그렇다면 예상되는 시나리오는 다음과 같습니다.
- 애플리케이션에서 DB로 요청 처리를 위한 쿼리를 전송.
- DB가 CPU 병목으로 쿼리 처리 지연
- 애플리케이션의 해당 요청 스레드가 응답을 기다리며 `waiting` 상태
- TPS 하락 (처리 완료까지 시간이 길어지므로 초당 완료 수가 줄어듦)

![Pasted image 20250715005606](/assets/images/performance-test-2/Pasted image 20250715005606.png)

예상대로 DB 서버의 CPU 사용률이 100%를 사용하고 있을 지점에 TPS가 급격하게 하락하면서, Latency 지표들도 급격하게 올라갔음을 알 수 있습니다. 

### 정리.

성능 문제가 발생했을 때 가장 먼저 해야 할 일은 **현재 시스템의 병목 지점**을 정확히 파악하는 것입니다. 이는 의사 선생님이 진료를 통해 정확한 진단을 내리고 치료 방법을 결정하는 과정과도 유사합니다.

현재 병목은 DB 서버에서 발생하고 있습니다. CPU 사용률을 분석한 결과, 피드 서버가 아닌 DB 서버에서 지속적으로 높은 부하가 걸리며, 사용률이 100%에 도달해 가장 바쁘게 동작하고 있음을 확인할 수 있었습니다.

이런 상황에서 피드 서버 쪽 스펙을 늘리거나, 스케일 아웃을 하거나, 스레드 풀을 확장하는 등의 조치를 취하더라도 **근본적인 문제는 해결되지 않을 가능성이 높습니다**. 병목이 발생한 지점을 정확히 짚지 않으면, 어떤 조치를 취하더라도 효과가 미미할 것으로 보입니다.


### 해결책들, 병목 개선안.

당장떠오르는 해결책과 시도해볼 수 있는 방법은 다음과 같습니다.

1. **리소스 설정 튜닝**    
    - DB 커넥션 풀 크기 조정
2. **DB 병목 원인 제거**
    - 인덱스 설정 및 쿼리 성능 분석
    - 필요 시, 새로운 DB 구조 도입 고려
3. **인프라 리소스 확충**
    - DB 서버 스펙 업그레이드

다만, **리소스가 많이 소모되는 방법은 가급적 후순위**로 두는 것이 바람직하다고 생각이 들었습니다. 인프라 증설은 가장 간단하면서도 즉각적인 해결책처럼 보이지만, 결국 현실적인 비용이라는 자원을 소비하는 일이기 때문입니다. 게다가 인프라 리소스는 단발성 비용이 아닌 지속적으로 발생되는 비용이라는 점도 고려를 해야합니다. 

또 근본적인 원인 해결이 되지 않는다면, 위와 같은 문제점은 또 다시 발생하게 될 것이고 그때마다 같은 방식으로 대응하는 것에도 확장성 측면에서 한계점이 있습니다.

물론 돈으로 해결할 수 있을만큼 무한한 재원이 있다면 굳이 백엔드 시스템을 최적화할 노력을 할 필요가 없겠지만, 가지고 있는 제한된 자원안에서 비즈니스 목표를 이룰 수 있도록 시스템을 최적화하는 것도 백엔드가 해야할 업무라고 느꼈습니다. 하지만 물론 성능상에 한계점에 도달했다면 리소스를 확충해야하는 시점이 올 수도 있습니다. 현재 가장 작은 스펙의 인스턴스를 사용중이기 때문에 그럴 가능성도 배제하기 힘들 수 있습니다.

따라서 인프라 리소스 확장은 마지막 수단으로 두고, 먼저 현재 구조 안에서 고민하면서 **최선의 성능을 낼 수 있도록** 시도해보려고 합니다.


### 문제 해결 시도


#### 쿼리 성능 분석 & 튜닝

`pt-query-digest` 분석도구를 통해서 슬로우 쿼리를 분석할 수 있습니다. 
다음은 성능 테스트 수행중 발생한 슬로우쿼리 로그를 분석한 결과입니다. 

```sql 
select *
from post p1_0 
where p1_0.publication='PUBLIC' 
	and MATCH(p1_0.title, p1_0.content) AGAINST('에러 해결 방법' IN NATURAL LANGUAGE MODE)>0 
	limit 0,10
```
현재 성능저하를 보여주고 있는 쿼리 구조는 위와 같습니다. MySQL의 전문 검색을 위한 FULLTEXT 인덱스와 여러 필터링 조건들이 포함된 쿼리입니다.

```sh
-> Limit: 10 row(s)  (cost=0.3 rows=0.5) (actual time=44.1..44.3 rows=10 loops=1)  
    -> Filter: ((p1_0.publication = 'PUBLIC') and ((match p1_0.title,p1_0.content against ('에러 해결 방법')) > 0))  (cost=0.3 rows=0.5) (actual time=44.1..44.3 rows=10 loops=1)  
        -> Full-text index search on p1_0 using full_text_index (title='에러 해결 방법')  (cost=0.3 rows=1) (actual time=44.1..44.2 rows=13 loops=1)
```

현재 인덱스 쿼리 분석시에는 그리 큰 부하가 걸리는 쿼리 같지는 않음. 


튜닝 제한, 

FULLTEXT 검색에서 관련도 순 정렬은 TF/IDF 계산이 필수적이라 근본적인 성능 개선에는 한계가 있었습니다




#### 리소스 튜닝, DB 커넥션 풀 개수?

🤔 DB 커넥션 풀의 수가 너무 적어서 그랬던 것은 아닐까? 

일단 첫번째로 드는 생각은 커넥션 풀의 개수를 늘리더라도 여전히 동일한 결과를 보일 것이었습니다. 일단 커넥션 풀의 개수가 의미하는 것은 DB서버에 요청을 보낼 수 있는 클라이언트 연결 수를 의미합니다. 만일 DB 커넥션 풀의 수를 조절해서 문제가 해결되려면, DB 서버의 자원(CPU 사용률)이 어느정도 여유가 있어야만 합니다.

그렇지만 앞선 테스트에서 DB 서버의 CPU 사용률은 이미 80%를 넘겨 100%에 가깝게 유지되고 있었습니다. 오히려 DB의 커넥션 풀의 수를 늘리게되면 그만큼 오히려 DB 서버에 부하가 갈 것같았습니다. 

대기 시간이 커넥션 풀 부족 때문에 발생하고, DB는 여유가 있는 경우에는 DB 커넥션 풀 개수가 병목 완화의 해답이 될 수 있을 것 같습니다. 

한번 예상한 내용이 맞는지 기존의 5개인 DB 커넥션 풀 개수를 최대 7개로 늘려서 테스트해보았습니다.  

(사진)

예상한대로 여전히 DB 서버의 부하로 인해 목표했던 성능 목표치에 못미치는 것을 확인할 수 있었습니다.


#### DB 버퍼풀 사이즈.
문서 수가 많고, 입력 키워드 조합이 다양할수록 계산이 많아짐. 주로 단어,키워드가 아닌 긴 문장형태의 검색어가 들어오는 경우 쿼리 

따라서 검색어가 길수록 더 많은 토큰이 생성되고 각 토큰의 결과를 모아 비교 연산을 수행하니 CPU에 가해지는 부하가 더 커지는 것으로 보임.

매 요청마다 다르게 입력되는 "자연어" 검색은 **캐시 효율도 낮을 것으로 보임** 그래서 InnoDB 버퍼풀에 캐시가 너무 자주

- 버퍼 풀이 비어 있어서 처음 몇 번의 쿼리는 **디스크에서 데이터를 읽고** 버퍼에 저장 
- 이후에는 **버퍼 풀에서 캐시된 데이터**를 읽으니 CPU 부하는 안정적 (예: 60%)
    
시간이 지나면서
- 쿼리 수는 일정하더라도, 다양한 데이터 접근이 계속되면 버퍼 풀이 점점 **새로운 데이터로 덮여쓰기**
- 이 과정에서 캐시 적중률이 떨어짐 → **디스크에서 다시 읽는 비율 증가**

결과적으로는 
- **디스크 I/O는 상대적으로 느리기 때문에** 그 데이터를 가공·정렬·필터링하는 데 더 많은 CPU 연산 필요    
- 또한 InnoDB는 **버퍼 풀에서 데이터를 정렬, 조인, 페이지 스캔 등 CPU 연산도 함께 수행**


때문에 DB의 버퍼풀 사이즈를 확인해봄. 보통은 인스턴스의 50% 이상을 둔다고 하는데 이도 적절한 테스트를 통해서 사용한다고 함. 현재 기본값은 128MB로 매우 작은 상태로 동작중이었음. 아마 예상하건데, 부하가 높았을 것으로 예상. 버퍼풀 사이즈를 늘려가며 해당 부분에서 병목 포인트였는지 테스트 해봄.

#### 슬로우 쿼리 분석.

```sql
SELECT ...
FROM post
WHERE MATCH(title, content) AGAINST('검색어')
  AND publication = 'PUBLIC'
ORDER BY id DESC
LIMIT 10;

```

```sh
id: 1
select_type: SIMPLE
table: p1_0
type: fulltext
possible_keys: idx_public_user_created_at, full_text_index
key: full_text_index
key_len: 0
ref: const
rows: 1
filtered: 50
Extra: Using where; Ft_hints: rank > 0; Using filesort
```

그리고 총 2개의 인덱스가 설정되어있는데요. 키워드 검색을 위한 `full-text-index`와 복합인덱스 2개가 존재합니다.  그 중

이 쿼리의 실행 계획을 확인해본 결과 먼저 눈에띄는 것은 `Using filesort`가 사용되고 있는 것이었습니다. Using filesort를 사용한다는 것은 정렬시, 인덱스를 타지 않고 정렬을 하고 있다는 것을 의미합니다.

🤔 id의 경우에는 PK, 클러스터링 인덱스를 타기 때문에 Using filesort가 일어나지 않을 것으로 예상했는데?
당연하게 id는 pk이기때문에 인덱스를 타기 때문에 정렬 조건에서도 무리 없을 것이라 생각했습니다.

이는 MySQL의 인덱스 사용방식 & OrderBy의 동작 방식과 관련이 있습니다.

👉[Mysql filesort의 의미]()

현재 실행계획에서 알 수 있는 것은 FullText 인덱스를 사용하고 있습니다. FullText 인덱스는 자체 랭킹(score) 정렬만 수행합니다. 그렇기 때문에, `ORDER BY id DESC`에 필요한 id 인덱스를 사용하지 않게 됩니다. 즉 pk 인덱스가 존재하더라도, 해당 인덱스를 타지 않습니다.

그렇다면 FullText 인덱스에 필요한 컬럼을 같이 추가해서 복합인덱스로 구성하면 되지 않을까?
결론부터 말하자면 불가능합니다. FullText 인덱스의 경우 복합인덱스 구성을 지원하지 않습니다.
