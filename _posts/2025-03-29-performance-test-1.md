## 목표 

진행하는 프로젝트에는 실제 트래픽이 존재하지 않고, 그에따른 사용자 패턴 데이터를 구할 수 없다는 한계점이 존재합니다. 때문에 가상의 서비스 모델을 설계하여 진행하였습니다.

서비스 특징  
- DAU = MAU × 0.4
	- DAU 전환율 (40%)
- 작성자 수 = DAU × 0.15
	- 작성자 비율 (15%)
- 1인당 작성량 = 1.5건/일

- 테스트 유형별 동시 사용자 수 증가율:
    - 부하 테스트: 기본 (100%)
    - 피크 테스트: +20%
    - 스트레스 테스트: +50%
누적 데이터 양 = 일일 작성 건수 × 180일 (6개월)

  서비스 모델로 설정. 증가폭은 2×씩 늘어나지만, MAU는 항상 **이전 단계의 2배**로 증가하는 **지수 성장 모델**로 가정.

동시 사용자 수 = DAU × (10분 체류 / 1440분) × 테스트 유형별 사용자 증가율
	- 평균 체류시간 = 10분 -> 테스트 수행 시간

TPS = 동시 사용자 수 / 2초 (Response + 평균 Think Time, 1~3초)

먼저 동시 사용자수를 가정한 후 목표 TPS를 설정하는 방식으로 진행했습니다.

리틀의 법칙(Little's Law)은 대기 행렬 이론에서 사용되는 공식으로, ==시스템 내의 평균 고객 수(L)는 평균 도착률(λ)과 평균 처리 시간(W)의 곱과 같다는 내용==을 담고 있습니다. 즉, L = λW 으로 표현됩니다.

[리틀의 법칙](https://engineering-skcc.github.io/performancetest/LittlesLaw/)

사용할 수 있는 자원에서도 한계점이 존재합니다. 실제 수익이 나는 서비스가 아니기 때문에 무작정 scale-up 해서 서버의 성능 향상을 기대하는 것도 적절하지 않다고 생각했습니다. 따라서 사용할 수 있는 서버의 스펙에도 제한을 둬서 수행했습니다.

## 테스트 API 

테스트할 대상 API는 피드 검색 api 입니다.

`/api/v1/feed/search`

검색 API 는 그 구성에 대해서 여러 종류가 있을 수 있음. 그중에서도 

> ✅ **“사용자가 특정 키워드를 포함하는 피드를 조회하는 경우”**  
> (즉, **키워드 기반 피드 검색**)

| 관점            | 설명                                                           |
| ------------- | ------------------------------------------------------------ |
| **사용자 행동 패턴** | 대부분의 유입은 검색어 기반으로 유도됨 (트렌드, 관심사, 태그 등)                       |
| **접근 빈도**     | 검색어는 홈 → 검색 → 피드로 이어지는 진입의 1순위                               |
| **UX/기능성**    | 키워드는 단독 또는 다른 필터(날짜/작성자 등)와 가장 많이 조합됨                        |
| **백엔드 부하 측면** | 키워드 검색은 일반적으로 인덱스 활용 여부, 쿼리 비용, full-text 여부에 따라 가장 성능 이슈가 큼 |
| **서비스 확장성**   | 추천/알림/랭킹 등에서도 키워드 기반 분석이 핵심이 됨                               |

에 대해서 집중적으로 테스트 해보려고함.


|순위|시나리오|이유|
|---|---|---|
|2️⃣|최신순 정렬 조회|홈/탐색 등 기본 흐름, offset 증가 시 부하 발생|
|3️⃣|키워드 + 날짜 or 작성자 조합|실제 사용자는 단순 필터보다 2가지 조건을 주는 경우가 많음|
후순위로 진행해보려고함.
