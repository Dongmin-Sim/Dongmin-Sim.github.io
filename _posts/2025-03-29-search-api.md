검색 API의 구현

테스트할 대상 API는 피드 검색 api 입니다.

`/api/v1/feed/search`

검색 API 는 그 구성에 대해서 여러 종류가 있을 수 있음. 그중에서도 

> ✅ **“사용자가 특정 키워드를 포함하는 피드를 조회하는 경우”**  
> (즉, **키워드 기반 피드 검색**)

| 관점            | 설명                                                           |
| ------------- | ------------------------------------------------------------ |
| **사용자 행동 패턴** | 대부분의 유입은 검색어 기반으로 유도됨 (트렌드, 관심사, 태그 등)                       |
| **접근 빈도**     | 검색어는 홈 → 검색 → 피드로 이어지는 진입의 1순위                               |
| **UX/기능성**    | 키워드는 단독 또는 다른 필터(날짜/작성자 등)와 가장 많이 조합됨                        |
| **백엔드 부하 측면** | 키워드 검색은 일반적으로 인덱스 활용 여부, 쿼리 비용, full-text 여부에 따라 가장 성능 이슈가 큼 |
| **서비스 확장성**   | 추천/알림/랭킹 등에서도 키워드 기반 분석이 핵심이 됨                               |

에 대해서 집중적으로 테스트 해보려고함.


|순위|시나리오|이유|
|---|---|---|
|2️⃣|최신순 정렬 조회|홈/탐색 등 기본 흐름, offset 증가 시 부하 발생|
|3️⃣|키워드 + 날짜 or 작성자 조합|실제 사용자는 단순 필터보다 2가지 조건을 주는 경우가 많음|
후순위로 진행해보려고함.



### 게시글 조회 기능 


처음에는 단순하게, 검색, 노출순(좋아요 최신순) 구분하지 않고 하나의 쿼리로 구현했음. 단순키워드 기반으로 검색어 필터링을 하는 방식으로 여러 정렬 조건들과 함께 사용했음. 

그런데 이 방식에서 MySQL 데이터베이스를 문제점이 존재.
#### 패턴 검색 느림 & 원하던 내용 X
Like 패턴 검색으로는 너무 느림.

 
#### 관련도 순 문제 발생 

 FullText index를 적용 -> 다른 노출순, 정렬과 맞지 않음.
키워드 검색의 의미가 옅어짐. 

기능을 분리.해서 
- 검색은 -> 관련도 순 
- 피드노출 -> 좋아요, 최신 순

### 검색과 노출순 기능 분리 (MySQL)

현재 구조에서는 키워드 검색 & 필터링을 구현하기가 쉽지 않은 구조이기 때문에 분리.

검색은 MySQL FullText index로 관련도 순으로만 

필터링, 정렬은 최신순, 좋아요순 노출은 별로도 수행하도로 구조 변경.
